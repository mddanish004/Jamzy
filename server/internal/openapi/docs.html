How Jamzy works, end to end.

Jamzy is a real-time social listening app: a room code, a shared YouTube queue, and one host whose play, pause, seek, and track changes every listener follows. This page documents the engineering behind it — the architecture, the PostgreSQL data model, the playback synchronization protocol, the control flows, the socket contract, the security posture, the deployment, and the full REST reference.

System at a glance

The product question is narrow: how do several browsers watch the same video at the same second without screen sharing? The answer shapes the whole system. The server owns playback state, PostgreSQL is the source of truth, and every client interpolates its playhead from the same timestamped snapshot.

Principle 01

Server-authoritative playback

The host's play, pause, seek, and track changes are database mutations. Each one stores a position and a UTC timestamp, then broadcasts the resulting snapshot. No viewer is trusted to drive another viewer's player.

Principle 02

State split by lifetime

Identity, rooms, membership, chat, and playback snapshots are durable and live in PostgreSQL. Presence, the queue, host-handover countdowns, and rate-limit windows are session state and live in guarded in-process memory.

Principle 03

Fail closed on identity

Both transports resolve identity from a verified Clerk session token. The backend never takes the caller's identity, host status, or role from a payload, and re-checks host authority against the database on every mutation.

Architecture

One Go binary serves the REST API, the Socket.IO endpoint, and this page. Persistence is a single PostgreSQL database. Clerk issues and signs the session tokens; the YouTube Data API supplies the catalog.

Concurrency model

  • Every socket event runs in its own goroutine, so slow database work cannot stall the transport.
  • Each handler recovers panics and logs the stack; a bad payload becomes one error acknowledgement, not a process exit.
  • Presence, queue, pending transfers, and per-connection room caches are maps behind mutexes.
  • HTTP routes are wrapped in recovery middleware that answers 500 without leaking internals.

State ownership

Durable (PostgreSQL): users, rooms including the playback snapshot, memberships, and chat history.

Ephemeral (process memory): presence, the queue, host-transfer countdowns, the per-connection joined-room set, and rate-limit windows.

The two meet once: the room:join acknowledgement returns presence, the persisted playback snapshot, the in-memory queue, and recent chat in a single round trip.

Request lifecycle

Recover → Request log → Security headers → CORS → ServeMux → RequireAuth → Rate limit → Handler → Service → pgx · SQL Authentication runs before the limiter, so a rate-limit bucket is keyed by the verified Clerk user rather than by IP. The health probe and this page bypass both; every other route takes the full chain.

Keys, indexes, and access paths

  • Uniqueness enforces product rules. One profile per Clerk subject, one owner per username, one room per code, one membership per user and room.
  • rooms_host_user_id_idx supports host lookups; room_members_user_id_idx supports eviction by user and “rooms I belong to”.
  • messages_room_id_created_at_idx covers the history window; the query adds id as a tie-breaker so pagination-free replays stay stable.
  • Presence and host succession read members ordered by joined_at ASC, user_id ASC, so the “longest-standing member” rule is deterministic and needs no extra column.
  • Room deletion cascades to memberships and messages; a host cannot be deleted while a room still references them because the host foreign key is RESTRICT.

Migration pipeline

The executable schema is the SQL in internal/db/migrations, embedded into the binary and applied on startup. prisma/schema.prisma is kept as the readable model and the reference for writing the next migration, but nothing executes it.

A session-level PostgreSQL advisory lock serializes concurrent booters, each migration and its version row commit in one transaction, and databases already migrated by Prisma are adopted by reading _prisma_migrations instead of replaying history. A new migration is one SQL file plus the matching change to the schema file.

Two consequences of dropping Prisma

Identifiers are generated in Go. Prisma's cuid() only ran inside the Prisma client, so the Go service generates CUID-shaped ids itself, mixing a millisecond timestamp, a per-process counter, and random characters.

Timestamps are formatted explicitly. Responses render times as 2006-01-02T15:04:05.000Z to match what the client parses, and JSON writers disable Go's default HTML escaping so song titles and chat text keep & characters intact.

Playback synchronization

Playback is not streamed as a position. The server writes a snapshot when the host acts, and each client derives the live position locally from that snapshot and its own clock.

expected = position + (now − updatedAt) × playbackRate position and updatedAt come from the last snapshot; now is the browser clock; playbackRate is the listener's local 0.5×–2× setting.

Why interpolate instead of streaming positions

  • Bandwidth stays flat: one event per action, not sixty per second.
  • Late joiners derive the correct position from the first snapshot, so the room does not need a replay buffer.
  • Buffering and tab throttling are absorbed locally; the server never waits for a player to catch up.

Drift correction on the client

  • A five-second interval compares the live YouTube player time with the derived expectation.
  • If the gap exceeds two seconds, the client silently seeks to the expected position.
  • Elapsed time is multiplied by the current playback rate, so the derived expectation tracks a listener who has changed speed instead of fighting the player.
  • The host runs the same logic; the host is not a special playback source.

The timezone bug this design had to survive

playback_updated_at is a PostgreSQL timestamp without time zone. On a database whose session zone was not UTC, writing now() stored local wall clock while pgx read it back as UTC, so joiners derived a negative elapsed time, clamped it to zero, and never caught up with the host.

All three playback writers now persist timezone('UTC', now()), making the stored value agree with the driver's UTC reads on every database. A committed regression test pins a scratch database to Asia/Kolkata, repeats a real leave-and-rejoin, and fails if any writer reverts to a zone-local now().

Control flows

The REST contract owns durable membership; the socket session owns live attendance. A browser joins a room twice — once over REST to persist membership, once over Socket.IO to receive state — and the two are linked only by the room code.

Room lifecycle (REST)

  1. Create: generate a six-character code from a 31-character alphabet that omits I, L, O, 0, and 1, then insert the room and the host membership in one transaction, retrying up to ten times on a unique collision.
  2. Join: resolve the caller, load the room, return it unchanged when the caller is already a member, otherwise insert with ON CONFLICT DO NOTHING and return the hydrated room.
  3. Leave: non-hosts delete their membership; a host with a successor updates host_user_id and deletes the membership in one transaction; the last member deletes the room, cascading memberships and messages.
  4. Hooks: leave evicts the user's sockets, clears any pending countdown, and announces the new host through an interface implemented by the realtime hub.

Host transfer

  1. Manual: the host names a member; the update only applies if the caller is still the host, then host:update is broadcast with reason manual.
  2. Disconnect: when the host's last socket drops, the hub arms a 30-second countdown and broadcasts host:pending with the likely successor and deadline.
  3. Return: any new socket from the host inside the window cancels the countdown and clears the pending banner.
  4. Expiry: members are read in join order, the first online member becomes host, and the role change is announced with reason disconnect.

Chat

  1. Validate the payload as non-empty and at most 500 UTF-16 units, matching the Node server's limit for emoji-heavy text.
  2. Re-check membership in the same query that resolves the room id, so a stale connection cannot post.
  3. Insert the message and join the author row in one statement; the database timestamp is the one broadcast.
  4. Broadcast chat:new to the room, then acknowledge the sender. Nothing is broadcast before the write succeeds.

Queue

  1. The queue is host-only and lives in memory, capped at 50 items.
  2. Add, prepend, remove, reorder, and clear each mutate the slice and broadcast the full queue.
  3. Advance dequeues the next track and writes it as a new playback snapshot; an empty queue clears playback.
  4. Every mutation replies with the authoritative queue after the broadcast, so a client never guesses the order.

Why broadcasts are emitted per socket

The Socket.IO library's adapter pre-encodes broadcast frames, and a defect in its WebSocket transport returns from the flush loop after writing a pre-encoded frame instead of continuing, silently dropping every packet behind it. In Jamzy the common case is a broadcast plus an acknowledgement in the same flush, so host actions lost their acknowledgements.

The fix avoids the defective path entirely: the hub looks up the room's socket ids and calls Emit per socket, which never marks a frame pre-encoded. The branch is structurally unreachable rather than avoided by timing, and the cost — encoding once per recipient instead of once per room — is irrelevant at this scale.

Security model

Authentication answers who the caller is; authorization answers what they may do. Both are enforced server-side on every transport, and neither trusts a field the client can set.

Authentication path

  1. Clerk completes sign-in in the browser and issues a short-lived session JWT.
  2. REST calls carry it as Authorization: Bearer …. Missing or malformed tokens answer 401 before any handler runs.
  3. The verifier parses the token header's kid, reads the matching key from an in-memory JWKS map refreshed at most hourly, and verifies signature plus claims. An unknown kid forces a refetch, which handles key rotation.
  4. The token's authorized party is checked against the configured origins, and an empty subject is rejected.
  5. The verified Clerk subject is resolved to an application user row; only that identity enters the request context.
  6. The socket handshake runs the same verifier on the connect payload and attaches the resolved user to the connection.

Transport and headers

  • CORS is an explicit origin allowlist with Vary: Origin, credentials enabled, and 204 preflight responses. Unlisted origins receive no CORS headers.
  • Responses set nosniff, SAMEORIGIN frames, no-referrer, HSTS for 180 days with subdomains, and same-origin opener policy.
  • There is no Content-Security-Policy: the API answers JSON, and this page is a self-contained document with inline styles and scripts and no third-party requests.
  • Socket.IO's HTTP upgrade passes through the logging wrapper, which forwards Hijack, Flush, and Unwrap so the handshake is not broken by instrumentation.

Failure behavior

  • Domain errors carry an HTTP status; handlers stay thin. Internal failures become a generic 500 and never leak SQL or stack traces.
  • Errors use a single message field, except unauthenticated REST calls, which also return authenticated: false.
  • Host-only refusals and other typed application errors are safe to display; unknown internal errors are replaced with a fallback message.
  • Panics are recovered per HTTP route and per socket event, logged with a stack, and contained to one response.
  • Malformed JSON is a client mistake and answers 400, not 500.

Operations and verification

The service is a single binary whose only hard runtime dependency is PostgreSQL and the Clerk secret; the YouTube key is optional, and music routes answer 503 without it. Migrations ship inside the binary, so deployment is a build and a restart.

Startup sequence

  1. Load configuration from the environment; values in the environment win over the optional .env file.
  2. Open the pgx connection pool to PostgreSQL.
  3. Apply embedded migrations under an advisory lock; adopt any existing Prisma migration history.
  4. Construct users, rooms, playback, messages, and music services, then wire them into the socket hub and router.
  5. Serve REST, Socket.IO, the docs page, and the health probe on 0.0.0.0:$PORT.
  6. Shut down gracefully on SIGINT or SIGTERM.

Test strategy

  • Sixty test functions across fourteen files. Unit tests sit beside the packages and need no database.
  • The end-to-end suite runs the real stack against a real PostgreSQL database and is skipped unless TEST_DATABASE_URL is set.
  • There is no Go Socket.IO client, so the suite includes a hand-written Engine.IO v4 client: it dials over Gorilla WebSocket, frames Engine.IO packets by hand, splits records on 0x1e, and asserts the packets a browser would receive.
  • A timezone regression test pins the database to Asia/Kolkata and repeats a real leave-and-rejoin, so the playhead contract is enforced, not just documented.
  • The Clerk verifier test points the SDK at a stub backend through an httptest server, exercising the cold-cache key fetch without network access.

Observability

  • Every HTTP request logs method, path, status, and duration.
  • Socket connects and disconnects log the user, socket id, and disconnect reason.
  • Host transfer decisions log the room, both hosts, and whether the trigger was manual, disconnect, or leave.
  • Rate-limit rejections and recovered panics log warnings and stacks respectively.
  • GET /api/health is the platform liveness probe and runs no authentication, database query, or rate limit.

Known limitations

  • Single instance. Presence, queue, countdowns, and rate windows live in process memory. A restart loses them, and a second instance would not share them; a Redis adapter and a shared store are the way out.
  • Cold starts. On free tiers the API and database sleep; the first request after a pause can take 30–60 seconds.
  • Clock skew. The playhead compares the browser clock with the server timestamp, so a badly skewed client can drift until the next reseek.
  • Documentation drift. The OpenAPI document is hand-written and must be updated with the handlers it describes.
  • No browser automation. The client is verified by a strict TypeScript build and a manual pass through the full flow, not by a committed browser test.

What scaling would require

  • Shared realtime state: move presence, queue, and pending transfers behind Redis and enable a Socket.IO adapter so any instance can broadcast to any room.
  • Distributed limiting: key fixed windows in the shared store rather than in each process.
  • Instrumentation: metrics for socket latency, broadcast fan-out, playback drift, and rate-limit rejections, with tracing across HTTP and socket paths.
  • Queue durability: persist queues per room if they should survive a restart or follow a room across instances.
  • Automated client smoke test: drive sign-in, onboarding, room creation, playback, and chat in CI.
